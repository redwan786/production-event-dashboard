# Render deployment guide

Render is optional for the brief. Finish and test the local demo first. This application has no login, access control, or rate limiting. A public Render URL can allow others to read and change data; use synthetic assessment data only and restrict access where possible. Do not expose a production database.

1. Complete the new Supabase setup, run migrations locally against the verified NEW assessment database, and push the project to your own GitHub repository. Never commit .env or credentials.
2. Sign into Render, select **New > Web Service**, connect GitHub if prompted and choose the correct assessment repository and branch. Choose the Node runtime. Set build command `npm install` and start command `npm start`. The app binds `0.0.0.0` to Render's provided `PORT` (local default 3000); do not hard-code a port.
3. In the service's Environment settings, privately set `DATABASE_URL` to the same NEW Supabase session-pooler URL. Remove sslmode or other SSL parameters from the URL because the application configures TLS itself. Set `CANDIDATE_ID` to `04` and `MQTT_URL` to `mqtt://152.42.238.142:1883`. Do not paste secrets into chat, GitHub, logs or screenshots.
4. Certificate verification remains enabled. If the pooler certificate is trusted by Node's default CA store, leave `PG_CA_CERT` and `PG_CA_CERT_PATH` unset. If a custom CA is needed, use the correct CA for the connection endpoint, supplied privately via `PG_CA_CERT` as PEM text or a Render secret file referenced by `PG_CA_CERT_PATH`. Do not disable TLS verification. Supabase's project CA and the pooler's public certificate chain may differ; consult the current Supabase connection settings. Session pooler normally supports IPv4 on port 5432; direct host connectivity may need IPv6.
5. Create/deploy the service. Inspect deployment logs for a listening message without sharing environment values. Open `/health` and the dashboard. `database: connected` verifies a query, not the project identity; verify the project reference separately. Ask the examiner to send a real MQTT challenge and verify the matching challenge ID and response in the simulator; connection alone is not success.
6. If startup fails, check build/start commands, Node version, environment variables and migration status. If database connection fails, check the correct project, password URL encoding, pooler host/port, CA trust and network access. If MQTT is disconnected, check outbound port 1883 and broker availability. Do not share secrets or raw logs containing them.

Free Render web services can spin down after inactivity. While asleep, MQTT and background processing stop; messages may be missed and recovery depends on the simulator and broker. A paid, continuously running service or local demo may be more suitable, subject to current Render policy. A deployment has not been verified in this project.
